# Mac の mod-tap の閾値を、Web UI の打鍵テストで実測しながら調整する

状態: 採用

2026-09-27 に、ADR 0044 で入れた `tapping_term_ms` を利用者の打鍵に合わせる手段として決めた。

## 背景

ADR 0044 は、mod-tap の tap と hold を閾値で分けた。
適切な閾値は打鍵の速さに依存し、実機で打ってみないと決まらない。
これまでの調整は手作業だった。
値を変え、適用し、別のアプリで打ち、結果を目で確かめる。
値ごとの成績も残らなかった。

- Fact: Karabiner は HID 層で入力を変換する。ブラウザの `keydown` は変換後のイベントである
- Fact: したがって、誤爆した chord（`⌥A`）、脱落、入れ替わりはブラウザで観測できる。押下時間は観測できない
- Fact: `keydown` の `preventDefault` で、ブラウザの ⌘A などは止められる。⌘Space・⌘Tab のように OS が先に取る組み合わせは止められない

## 選択肢

1. 実測: 閾値を Karabiner へ適用し、課題を打った結果をブラウザで採点する
2. 記録と模擬: KeySync の mod-tap を外した状態で素の打鍵タイミングを記録し、Karabiner の判定を模擬して各閾値の結果を一度に出す
3. 1 と 2 の併用

## 決定

案 1 を採る。

- Web UI に Mac 専用の「打鍵テスト」パネルを足す。同じ画面で、閾値を変える、Karabiner へ適用する、課題を打つ、採点する、閾値ごとに比べる、を行える
- 適用は既存の「Karabiner へ適用…」をそのまま使う。手順と確認は ADR 0034 のまま変えない
- 打った結果には、Karabiner で効いていると確かめた閾値を付ける。確かめたと扱うのは次の 2 つだけである。確かめていない試行は「未確認」として分ける
  - このセッションで適用が成功したとき
  - 差分が無く、profile も選択済みだと分かったとき
- 課題は既定のロール集、keymap の mod-tap から作る hold 課題、自由入力の 3 種類にする
- 採点と集計は Semantic Core（`src/core/typing-trial/`）に置き、DOM に依存させない
- 試行の記録は画面の state に持ち、再読込で消える

## 理由

- **模擬は実物と一致する保証が無い。** Karabiner の `to_if_alone`・`to_if_held_down`・`to_delayed_action` の組み合わせの細部（イベントの順序など）は公式に書かれておらず、模擬が外れると調整を誤る
- **実測は ADR 0044 の Open Question も確かめられる。** 文字順の入れ替わりは、採点の `swapped` として直接出る
- **案 2 は profile の切り替えを要する。** ADR 0022・0034 は KeySync が所有する profile 以外に触らないと決めている。素の打鍵を記録するために他の profile を選ぶと、この境界を越える
- **hold 課題を keymap から作る。** 割り当てを変えても課題が追従し、手書きの課題と keymap がずれない
- **記録を永続化しない。** 調整は 1 回の session で終わる作業で、後から読み返す要件が無い

## 影響

- 閾値を変えるたびに適用が 1 回要る
- OS が先に取る chord（⌘Space など）は防げない。spacebar の mod-tap が誤爆すると Spotlight などが開くことがある
- IME はオフ（英数）で打つ必要がある。変換中の入力が混ざった試行は採点しない
- Rail の入口に専用のアイコンが無い。`src/ui/icons/` は外部で描いた SVG を写す運用のため、当面は keymap のアイコンを借りる
